## 一言まとめ

「良いコードを書く」よりも「良い判断を続けられるプログラマーになる」ための考え方を、原則の形で整理してくれる一冊。個別のテクニックよりも、日々の設計判断の土台になる **原則の言語** が手に入るのが最大の価値。

## 刺さったポイント

### 1. DRY 原則 (Don't Repeat Yourself)

- 「すべての知識は、システム内で単一かつ明確で信頼できる表現を持たなければならない」
- 重複するのは **コードではなく知識**。同じ知識が 2 か所にあると、片方だけ変わって矛盾が生まれる
- コードのコピペだけでなく、ドキュメントとコードの重複、DB スキーマとモデル定義の重複、コメントとロジックの重複も DRY 違反
- 逆に、たまたま似ているだけのコードを無理に共通化するのは DRY ではない（知識が違えば別物）

> [!tip] 自分への問い
> 「この変更、他にも直さないといけない場所はないか?」と聞かれたら、それは DRY 違反のサイン。

### 2. 直交性 (Orthogonality)

- あるコンポーネントを変更しても、他のコンポーネントに影響が出ない状態
- 直交性が高いと **生産性** (変更が局所化する・再利用しやすい) と **リスク低減** (壊れる範囲が小さい・テストしやすい) の両方が得られる
- 「これを変えたら、どこまで波及するか?」を常に意識する
- DRY と直交性はセット。DRY は重複を減らし、直交性は依存を減らす

### 3. 曳光弾 (Tracer Bullets)

- 暗闇で銃を撃つとき、曳光弾で軌道を見てから狙いを修正するように、**最初から端から端までつながる細い一本の実装** を作り、そこから肉付けしていく
- プロトタイプとの違い
  - プロトタイプ: 使い捨て。特定の疑問を検証するためのもの
  - 曳光弾: 捨てない。本番と同じアーキテクチャで、機能が薄いだけ
- 早い段階でユーザーに動くものを見せられる、統合の問題が最初に出てくる、進捗が測れる
- 自分の開発スタイルにもっとも取り入れたい考え方。スキーマ → API → UI と層ごとに作るより、まず 1 ユースケースを貫通させる

### 4. 割れ窓理論 (Broken Windows)

- 割れた窓を放置すると建物全体が荒れていくように、**放置された悪いコード** (不十分な設計・雑な実装・回避されていない警告) は「ここは手を抜いていい」というメッセージになる
- 割れ窓を見つけたらすぐ直す。すぐ直せないなら、少なくとも板を打ちつける (コメント・TODO・ダミー実装で「気づいている」ことを示す)
- チームの文化としても重要。自分が最初の割れ窓を作らない

> [!warning] 反面
> 「割れ窓を直すこと」を口実に、火事の最中に窓の修理をしてはいけない (優先度の判断は別)。

### 5. 契約による設計 (Design by Contract)

- Bertrand Meyer の考え方。関数・メソッドが守るべき約束を明示する
  - **事前条件** (precondition): 呼び出し側が満たすべき条件
  - **事後条件** (postcondition): 呼ばれた側が保証する条件
  - **不変条件** (invariant): 常に真であるべきクラスの状態
- 「怠惰なコード」を書く: 受け入れる前に多くを要求し、返す前に少ししか約束しない
- 契約を破ったら早めにクラッシュさせる (Crash Early)。壊れたプログラムを動かし続けるほうが被害が大きい
- 実装面: 型・アサーション・バリデーションを「契約の表現」として意識的に使う。TypeScript なら型で事前条件を、テストで事後条件を表現できる

## その他のメモ

- **ETC (Easier To Change)**: 良い設計とは変更しやすい設計。DRY・直交性・疎結合はすべて ETC のための手段
- **偶発的プログラミングを避ける**: なぜ動いているのか分からないコードを書かない。意図してプログラミングする
- **十分に良いソフトウェア**: 完璧を目指すよりも、いつ止めるかを知る
- **知識ポートフォリオ**: 学びは投資。定期的・分散的に、リスクを取って学ぶ

## 学びをどう活かすか

- [ ] 新規機能を作るときは、まず曳光弾で 1 ユースケースを端から端まで貫通させる
- [ ] コードレビューで「同じ知識が 2 か所にないか?」「この変更の波及範囲はどこまでか?」を確認観点にする
- [ ] 関数の先頭で事前条件を明示的に検証する (早期リターン / アサーション) 習慣をつける
- [ ] 小さな割れ窓 (警告・雑な命名・放置 TODO) を見つけたら、その PR の中で直すか Issue 化する
